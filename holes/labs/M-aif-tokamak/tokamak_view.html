MetaCA Tokamak — what it is, what was broken, and the one decision I need

Regenerated 2026-07-15 from live measurement. Every number below is measured, not illustrative. Supersedes the previous tokamak_view.html, which described an apparatus that turned out not to be connected.

The decision, up front

The plant fights back. The tokamak's reachable set — the set of macro-states it can actually steer to — is not fixed. It shrinks because the controller acts. Measured, from an identical start, 6 windows later:

what the controller didhighest pressure it can still reach afterwards
held still (6× :hold)0.336
mixed rotations0.208
rotated steadily (6× :rotate-down)0.188

So acting costs future control authority. Steering toward the high-pressure corner is what destroys the high-pressure corner. That is not a bug — it is what this system is. But it means "hold the CA at a target C" is the wrong question, and I need you to pick the right one.

Option 1 — Freeze the genotype. Regulate a stationary plant.

run-mmca already supports :freeze-genotype. The reachable set stops moving, and claim (A) becomes textbook set-point regulation.
Buys: a clean, unambiguous control result, in about an hour. A floor.
Costs: the genotype is the "Meta" in MetaCA. Freeze it and you are controlling a fixed-rule CA — a simpler system that arguably isn't the object of study.

Option 2 — Keep a fixed target in channel space, and accept it drifts out of reach.

Buys: nothing much. Costs: when the controller misses, you cannot tell whether it failed or whether the target left the reachable set. Measured: target B is unreachable by t=6. This option is here only because it is what the demo currently does, and I want to be explicit that I think it should be dropped.

Option 3 — Target a relative objective: "stay at the max-pressure corner of your own current reachable set."my recommendation

The target is re-derived each window against what the plant can currently do.
Buys: robust to drift by construction; it's what a real tokamak does (hold a plasma at an operating point as the plasma moves); and it is exactly the problem R13's horizon exists for — a myopic controller spends authority it will need, a horizon-aware one preserves options.
Costs / the catch you should weigh: circularity risk. If C is defined as "wherever the plant can go", is "reaching C" tautological? I think no — at each window there are 8 rotations and only one is the corner, so finding it requires real prediction, and :null demonstrably fails to track it. But that is a judgement call about what counts as a claim, which is why it's yours and not mine.

My read: Option 1 first as a one-hour sanity floor (does the loop regulate anything?), then Option 3 as the real claim. And if Option 3 is right, then this testbed isn't a "tokamak controller" at all — it's a niche-construction problem, where the agent modifies its own affordance landscape. That's M-aif2, arriving here on its own.

1. The loop, in one paragraph

A MetaCA is a string of 8-bit "sigils" (the genotype) that evolves like a cellular automaton. An exotype perturbs the update kernel each tick. The tokamak is an active-inference controller: each window it observes macro-features, predicts what each candidate action would do (R4), scores them against a target C by expected free energy (R5), and picks one. The two macro-features it scores are pressure (rate of change) and selectivity (template-matching). Signal, in your earlier question, is precisely these two numbers — that is all the controller can see.

2. The actuator: it is exactly Z/8

The only thing the controller can physically do is rotate the sigil. Verified to 1e-9: rotate-left k ≡ rotate-right (8-k), so the two "knobs" are one signed rotation r ∈ Z/8. All 8 rotations give distinct macro-states. That is the whole action space.

The reachable set at t=0 (8 points, one per rotation). The EoC target (red) is where we'd like to be. Note it sits off the selectivity axis entirely — no rotation reaches it.
The same set after 6 windows (orange) versus t=0 (blue). The plant has moved. Target B, chosen at t=0, is no longer reachable.

3. What was broken (all three, at once)

Every component passed its tests. The experiment was still meaningless — three independent defects, each sufficient on its own to make the controller indistinguishable from no control.

3a. The action space actuated knobs that do nothing

knobsweptwindows it changed the plantmean effect
Why nobody noticed: the test suite asserted "pressure-up increases update-prob" — which is true. It checked that the wire was connected, never that the field mattered. A green test certifying a no-op. This is the cyberant bug exactly: wiring written, never read.

3b. A silent catch disabled the whole actuator

A genotype-derived operator (BlendHand) set a kernel with no spec; kernel-spec-for threw; (catch Exception _ nil) swallowed it; the exotype path short-circuited on every tick and the run still reported success. Measured: 0 exotype mutations with genotype-derived operators, 105 with them disabled.

3c. The comparison itself was confounded

forward-predict is documented as "one pure forward kernel" (R4) and drew from global rand. The :aif arm burns RNG running rollouts; :null doesn't. Smoking gun: a trial where :aif chose :hold for all 12 windows — an arm identical to null by construction — still reported a different result. Now fixed and pinned by a test; identical action sequences now agree to the last digit.

Honest status: claim (A) is still not validated. Two problems, both mine:
  • Phase 1 is degenerate. I made target A the min-pressure corner, which is where the run already starts — so holding is optimal, null also holds, and the arms are identical by construction. It cannot discriminate. Windows 0–6 above are the proof.
  • Phase 2 can't be reached. The controller moves toward B (closer than null in 4/5 trials) but never arrives — because rotating toward B collapses the reachable set that contained B.
The actuator is live, the arms are paired, the targets are reachable and discriminable at t=0. The experiment is now well-posed, and what it reveals is that the question was wrong. Hence the decision above.

5. How the evaluation is set up (the gates)

These are the checks that would have caught all of the above, and they run in about two minutes (futon5.aif.design-gates). They are preconditions, not analyses — because a dead knob makes an ablation pass for free:

gateasksold design
1. actuator authoritydoes each action move the plant? (paired)FAIL — 0.000 on every action
2. target reachabilitycan the plant reach C at all?FAIL — both targets outside
3. arm discriminabilitydo A and B induce different behaviour?FAIL — same optimum (r=6)
4. non-stationarityis C still reachable later?FAIL — B gone by t=6
Gate 3 is the one worth staring at. Both targets had the same nearest reachable point, so a competent controller must do the same thing in both arms. The demo's own stated falsifiable core reads: "a controller that collapses to the same place regardless of C is dying, not confining." It would have scored correct behaviour as death. The experiment could not have produced evidence either way.
"Scramble the wiring → same results" is the signature of a disconnected actuator. It is equally well explained by "the wiring never mattered" (refuting the hypothesis) and by "the wiring was never read" (refuting the apparatus) — the null cannot tell them apart. That is what the original cyberant refutation ran into, and you called it on day one: "even the original wiring may have been bad wiring."
